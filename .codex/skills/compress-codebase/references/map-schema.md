# File map and handoff schema

## Artifacts

Maintain two artifacts:

- An exhaustive TSV ledger generated by `scripts/inventory.py` and completed by
  the agent. It is the coverage authority.
- A narrative Markdown map explaining target architecture, cross-file collapses,
  ordered slices, budgets, invariants, and validation. It is the handoff.

Use user-requested paths. Otherwise keep the working ledger beside the skill and
put a durable handoff in `docs/` only when the work is a real design decision —
in that case follow `vkr-docs` for front-matter and index registration.

## Ledger columns

| Column | Required meaning |
| --- | --- |
| `file` | Repository-relative original path. Never replace it with a directory aggregate. |
| `language` | Inventory classification (`c`, `header`, `slang`, `json`, `other`). |
| `lines`, `nonblank`, `comment_lines`, `branch_tokens`, `assert_tokens`, `bytes` | Deterministic baseline proxies from the inventory script. They guide inspection; they are not deletion quotas. |
| `disposition` | `keep`, `compress`, `deepen`, `merge`, `delete`, `move-private`, `split`, or `generated-asset`. |
| `slice` | Ordered vertical slice that owns implementation of this row. |
| `owner` | The one surviving file/module and the authoritative fact or lifecycle it holds. |
| `action` | Concrete deletion, consolidation, or retained reason. Name peers and callers. |
| `expected_lines` | Target or expected deletion band, including replacement code. Leave blank when evidence cannot support one. |
| `current_lines`, `delta_lines` | Final reconciliation against the baseline; deleted files use zero current lines. |
| `risk` | Behavior, ABI, ownership, concurrency, lifetime, visual, build, or performance risk. |
| `validation` | Planned evidence owner: focused test, `./build_test.sh`, validation-layer run, benchmark, build, or a justified none for map-only work. |
| `status` | `unreviewed`, `mapped`, `in-progress`, `complete`, `superseded`, or `blocked`. |
| `evidence` | Actual command, result, or artifact — or the concrete reason validation was unavailable. |

Do not mark a row complete with "simplify", "clean up", or "reduce checks".
State which representation disappears, which owner survives, and why its proof
remains sufficient.

## Dispositions

- `keep`: deliberately irreducible or a justified seam. This is coverage, not a
  missed opportunity.
- `compress`: preserve responsibility in place while deleting duplicate paths,
  states, fields, checks, or comments.
- `deepen`: absorb repeated policy from peers into this surviving owner. Count
  its added lines against deleted peer code.
- `merge`: migrate behavior into the named owner, then delete this file.
- `delete`: behavior is dead, generated elsewhere, or pure forwarding.
- `move-private`: retain real behavior but remove unnecessary public surface —
  in C this usually means dropping a declaration from the `.h` and marking the
  definition `static`.
- `split`: use only when lifecycle or locality improves and total relationships
  or maintained LOC falls. File count alone may rise.
- `generated-asset`: move a generated payload out of maintained source with
  provenance, deterministic generation, size/hash checks, and build integration.

## Narrative map

Include:

1. Scope, commit, exclusions, baseline metrics, and target band.
2. Non-negotiable behavior, ownership, concurrency, lifetime, and performance
   invariants.
3. One-fact/one-owner target shape, and the check/comment policy.
4. Compression budget by vertical slice, expressed as planning bands rather than
   independent per-file quotas.
5. Ordered implementation program with migration and deletion boundaries.
6. Validation contract assigning each invariant to the correct evidence surface.
7. The complete file disposition ledger, or a link to the TSV.
8. Coverage reconciliation proving every initial file is represented.

## Vertical-slice record

Before each implementation slice, record:

- exact files and physical LOC before editing;
- at least two concrete repeated cases;
- the one surviving representation and its owner;
- checks removed, and the seam that retains the proof;
- allocation, lock, string, indirection, and wait effects in hot paths;
- borrowed views, storage stability, handle acquire/release symmetry, and
  completion-gated retirement where applicable;
- expected net LOC and file delta;
- the smallest complete validation, and any baseline limitations.

After the slice, record actual totals and any newly created files. Reject
apparent compression that only transfers lines into an uncounted helper.

## Coverage reconciliation

Compare the initial inventory, the final inventory, and the ledger:

- every initial file has exactly one disposition;
- every deleted path names its surviving owner, or its dead/generated reason;
- every new file is counted and justified as a deep owner;
- retained files are explicit;
- ledger totals equal the defined scope after exclusions;
- superseded targets and architectural exceptions carry evidence, not silence.
