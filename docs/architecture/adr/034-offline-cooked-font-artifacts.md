# ADR-034: Offline-cooked font artifacts

## Status

Proposed. No production code implements this decision.

## Context

VKR carries three font paths with three delivery formats and three metric
conventions.

The MTSDF path consumes a checked-in msdf-atlas-gen JSON plus a sibling PNG,
named from a `.fontcfg` and resolved through a query string
(`file.json?atlas=...&size=18`). Nothing in the repository produces those files.
They were generated by hand with the msdf-atlas-gen CLI at some point and
committed. `assets/fonts/Ubuntu-2d.json` contains `"kerning": []` because the
invocation omitted `-kernpairs`, and there is no record of the command, the
charset, the distance range, or the packer settings that produced it.

The consequences are recorded in
[text-resolution-independence-and-font-cooking-spec.md](../../text/text-resolution-independence-and-font-cooking-spec.md)
§2. The ones this decision addresses:

- The JSON is parsed by `vkr_json_find_field()`, which tracks no brace depth. A
  lookup for `atlas.emSize` — a field msdf-atlas-gen does not emit there — runs
  past the object and returns `metrics.emSize`. The font loads correctly only
  because that value happens to be `1`.
- `atlasBounds` are half-texel floats. The loader truncates them into
  `uint16_t`, biasing every glyph's UV rectangle by half a texel on both axes.
- The atlas PNG lives in `assets/textures/`, so `vkr_vkt_packer` sweeps it up,
  classifies it `color-srgb` by filename, and emits a UASTC-compressed,
  sRGB-tagged, mipmapped sidecar. The KTX2 key/value block in
  `assets/textures/Ubuntu-2d.png.vkt` records
  `class=color_srgb;uastc=faster;mips=rgba8-box-v1`. Block compression breaks
  the channel independence that `median3` requires, and an sRGB view applies the
  EOTF to distance values. The runtime asks for linear UNORM and the cooked
  sidecar's class overrides it.
- The MTSDF loader separately re-opens the source PNG and decodes a full RGBA
  copy into `VkrFont::atlas_cpu_data`, which no code in the repository reads.
  For the 2048² 3D atlas that allocation exceeds the 6 MiB arena-pool chunk and
  logs a failure at every startup.

The repository already has the right shape for the fix. ADR-012 established
offline KTX2/UASTC texture packing with a content-hash skip and build-wrapper
integration. ADR-030 established `vkr_mesh_cooker`, a pinned `vendor/`
submodule, an offline cooking step, and a versioned binary runtime artifact
whose ABI is ADR-031. A font cooker is the same pattern applied to a third asset
class.

`nuri` — the other renderer in this workspace — already implements exactly this.
`compileNFontFromFontFile()` links msdf-atlas-gen directly, drives
`FontGeometry::loadCharset` → `edgeColoringInkTrap` → `TightAtlasPacker` →
`ImmediateAtlasGenerator<float, 4, mtsdfGenerator>`, and serializes metrics,
`pxRange`, float glyph records with pre-normalized UVs, a codepoint map, and the
atlas pixels into one binary `.nfont`. Its runtime library links no msdf code;
the dependency sits only in the editor target.

## Decision

Adopt msdf-atlas-gen as a pinned, static dependency of a new offline
`vkr_font_cooker` tool, and make a versioned binary `.vkfa` container the sole
cooked-font delivery format.

**Dependency.** `vendor/msdf-atlas-gen` as a git submodule pinned to a specific
commit, following `vendor/ktx-software` and `vendor/meshoptimizer`. CMake builds
it as a static child target. A missing checkout fails configure with the normal
submodule-initialization instruction. Configure performs no network download.
msdf-atlas-gen and msdfgen are linked **only** into the `vkr_font_cooker`
target. Neither `renderer_lib` nor any runtime translation unit gains an msdf
include path or a C++ dependency.

**Tool.** `tools/vkr_font_cooker.cpp`, a sibling of `vkr_vkt_packer.cpp` and
`vkr_mesh_cooker.c`. It reads a `.fontcfg`, produces one `.vkfa`, and skips
content-identical outputs unless forced. The root build wrappers invoke it after
a successful compile and treat cooking failure as build failure, matching the
texture packer's contract. Standalone `tools/cook_vkr_fonts.sh` and `.bat`
wrappers exist for forced or strict preparation.

**Container.** `.vkfa`, magic `VKFA`, little-endian, versioned from 1. `.vkf` is
already taken by the version-1 BMFont cache with magic `VKFT`, which the bitmap
loader claims in its `can_load`; overloading that extension would make loader
selection ambiguous. The container holds:

- header: magic, version, source content hash, page count, glyph count, kerning
  count;
- `float32_t distanceRange` in atlas pixels and `float32_t atlasPxPerEm`;
- em-normalized font metrics: ascender, descender, line height, underline
  position and thickness, `unitsPerEm`;
- a glyph table sorted by glyph index. Every field is `float32_t`: advance,
  plane bounds, and UV bounds **already normalized to [0,1] with the V flip
  applied**. Plus a `uint16_t` page index;
- a codepoint→glyph-index table sorted by codepoint, for binary search or a
  direct integer-keyed hash;
- a kerning table sorted by packed codepoint pair, amounts in `float32_t` em
  units;
- atlas pages as uncompressed pixels, `R16G16B16A16_SFLOAT` by default, one mip
  level.

No field in the container is expressed in pixels of a chosen render size. The
runtime never divides by an atlas extent, never truncates a bound, and never
infers a Y convention.

The container reserves space for glyph identifiers distinct from codepoints, so
a shaper can be added later without a format break. Shaping is not part of this
decision.

**Atlas format.** `R16G16B16A16_SFLOAT`, uncompressed, single mip. Sixteen-bit
float removes the 8-bit distance quantization; uncompressed removes the
block-correlation failure; a single mip removes box-filtered pseudo-MSDFs. Font
atlases do not enter the `vkr_vkt_packer` input set, and the packer gains an
explicit skip so a stray loose atlas cannot be misclassified.

**Runtime.** A new loader decodes `.vkfa` in the existing `VkrResourceLoader`
vtable, in C11, keeping the current resource type, arena-pool ownership, and
render-thread finalization model. The JSON+PNG MTSDF loader remains registered
until assets migrate, then is retired.

## Consequences

Font generation becomes reproducible. The charset, distance range, atlas
dimensions, packer settings, and edge-coloring parameters live in the
`.fontcfg`, and the cooker records a source content hash in the artifact. Two
runs on the same input produce byte-identical output, matching ADR-030's cooker
contract.

The half-texel UV bias, the brace-unaware JSON scan, the packer
misclassification, and the discarded `atlas.size` all disappear as a class,
because the runtime stops deriving anything.

`atlasPxPerEm` and `distanceRange` reach the shader as cooked facts, which is
what [ADR-035](035-canonical-mtsdf-screen-pixel-range-shading.md) needs.
`float32_t` glyph metrics are what [ADR-036](036-dpi-derived-ui-text-scale.md)
and the spec's float layout conversion need. The three decisions are separable
but F2 in the spec's plan needs all three.

Build time grows by one MSDF generation pass per font, which is the expensive
part of cooking and is multithreaded in msdf-atlas-gen. The content-hash skip
means it runs once per font change, not per build.

Resident atlas bytes grow. A 1024² RGBA16F page is 8 MiB against 4 MiB for
RGBA8 and roughly 1.3 MiB for UASTC with mips. A build carrying three font
atlases pays on the order of 20 MiB. The spec's evidence gate requires a
measured Release comparison rather than an assumption that this is free.

Repository size grows: the atlas pixels move from a compressed PNG into an
uncompressed container. Cooked `.vkfa` artifacts are build outputs and should be
git-ignored, with the `.fontcfg` and the source `.ttf`/`.ttc` as the committed
inputs — the same split ADR-030 uses for `.vkb`.

A new C++ submodule enters the build. msdf-atlas-gen pulls msdfgen, which pulls
FreeType. FreeType is a new transitive dependency for the tool target only. This
is the main cost of the decision and the main reason the dependency is confined
to a tool.

## Alternatives Considered

**Keep JSON + PNG, fix the parser and the packer classification.** Cheapest, and
it is what the spec's F0 stage does as an interim step. It fixes the sRGB and
block-compression corruption and the `emSize` scope escape. It does not fix the
half-texel truncation without a runtime float rewrite anyway, does not make
generation reproducible, does not produce kerning, and leaves two files and a
query-string protocol as the delivery contract. Worth landing as a stopgap;
not worth landing as the destination.

**Shell out to the msdf-atlas-gen CLI from a build script.** No submodule, no
C++ target, no FreeType. Rejected because it makes the toolchain an unversioned
environment dependency, cannot emit a custom container, cannot record a source
hash, and gives no error path a build wrapper can treat as failure in the way
ADR-012 and ADR-030 require. It also reproduces the current situation: an
external tool whose exact invocation is not captured anywhere.

**Generate MSDFs at runtime on first use, cached to a sidecar.** Removes the
build step and supports dynamic glyph sets. Rejected: it puts msdfgen and
FreeType in the runtime library, makes first-frame cost unbounded, and
contradicts ADR-012 and ADR-030's established direction of moving asset
preparation offline.

**Embed the atlas as a `.vkt` sibling rather than inside the container.**
Reuses the existing versioned texture delivery and its transcode cache. Rejected
because it reintroduces two files and two hashes for one asset, and because
every `.vkt` policy knob — compression, mip generation, colorspace class — is
the wrong default for a distance field, so the font would need to opt out of all
of them. Recorded as the leading alternative if atlas residency becomes a
measured problem.

**Extend the existing `.vkf` bitmap cache to version 2.** Rejected: the bitmap
loader's `can_load` already claims `.vkf`, the formats share no fields, and
ADR-030's precedent is a distinct extension per cooked asset class.

## Revisit When

- Atlas residency shows up in a measured heap-pressure or streaming report. The
  `.vkt`-sibling alternative becomes the answer, or RGBA8 becomes the default
  with RGBA16F opt-in.
- A font needs a glyph set too large to cook ahead of time — a full CJK face
  with variable coverage. That is a dynamic-atlas decision this ADR does not
  make, and it would need its own ADR rather than a change to this one.
- Text shaping is adopted. The container reserves glyph-id space, but a shaper
  changes what the cooker must emit and adds a HarfBuzz-class runtime
  dependency.
- msdf-atlas-gen's API changes incompatibly at a pin bump. The pin is explicit
  precisely so this is a deliberate action.
