# Meshoptimizer Geometry Loading and Packing Specification

## Conclusion

VKR integrates [meshoptimizer](https://github.com/zeux/meshoptimizer) through
offline version-15 `.vkb` cooking, mandatory runtime source optimization, and
glTF `EXT_meshopt_compression` input decode. The worker
validates complete artifact integrity and embedded dependency provenance,
decodes packed streams into its result arena, and publishes the same 32-byte
static geometry ABI on Metal and Vulkan. Runtime decode does not reopen
authoring dependencies to revalidate their current identity.

Meshoptimizer's codec reduces cooked bytes; ADR-031 packing separately halves
vertex upload and residency bytes. Production scenes reference cooked
artifacts generated by `tools/cook_vkr_meshes.sh` or
`tools/cook_vkr_meshes.bat`. Version 15 is self-contained at runtime:
dependency paths, sizes, and SHA-256 data remain offline provenance, while
decode reads no authoring inputs.

The measured 24-byte float16-UV candidate was rejected: New Sponza range 26
produced 7.8418 absolute UV error against the 0.02 budget. The implemented
32-byte layout preserves float32 UVs, packs position/normal/tangent/color, and
keeps one branchless static decode path in both selected backends.

## Current implementation

### Resource scheduling and ownership

`vkr_resource_system_load()` deduplicates an asynchronous request by
`<resource type>|<path>`. Meshes are async-by-default: the worker invokes a
loader's `prepare_async`, queues the payload, and the render-thread
`vkr_resource_system_pump()` invokes `finalize_async` within its request and
upload budgets. A `VkrMeshLoaderResult` owns its CPU data through a dedicated
arena or a returned `VkrArenaPool` chunk; `vkr_mesh_loader_destroy_result()`
destroys/releases that storage after the mesh manager has published it.

This is a sound ownership boundary for a decoded cooked mesh:

```text
source/cooked bytes (worker scope)
  -> decoded result buffers (mesh-result arena)
  -> render-thread material dependency resolution + geometry publication
  -> GPU-owned buffers; loader result released when the resource reference ends
```

Mesh load and renderer metrics cover the requested dependency closure, cooked
artifact, decoded CPU payload, upload totals, megabuffer live/high-water bytes,
decode metadata, element/range counts, and meshoptimizer analyzer results.

### Mesh ingestion and cache

The single `VKR_RESOURCE_TYPE_MESH` loader dispatches `.obj`, `.gltf`, `.glb`,
and `.vkb`. Source requests parse authoring data without writing a sidecar.
Explicit `.vkb` requests enter the version-15 validator/decoder. It remains one
loader because ordinary batch routing is by resource type; a second mesh loader
would not safely route mixed formats. The glTF design documents the same
constraint in [gltf-loader-design.md](gltf-loader-design.md).

For each material bucket, `vkr_mesh_loader_finalize_builder()`:

1. deduplicates byte-identical `VkrVertex3d` vertices;
2. generates tangents and computes bounds;
3. appends vertices and indices to the request-local source result;
4. applies mandatory cache/fetch optimization per range;
5. packs the final merged result before it is committed to the result arena.

Version-12 through version-14 `.vkb` files are stale. `vkr_mesh_cooker` is the
sole version-15 writer; each material range has separately
cache/fetch-optimized, quantized, and meshoptimizer-encoded packed-vertex and
`uint32_t` streams. The artifact records SHA-256 dependency/settings identity,
optimized bounds, material metadata, aligned streams, quantization budgets/maxima,
encoded/decoded sizes, and CRC32 metadata/stream checksums.

The glTF importer reads every accessor into temporary `VkrVertex3d` and bakes
each node's world transform into its vertices before it emits a primitive.
Consequently, repeated glTF mesh nodes can become separate transformed geometry
inside one loaded resource. Meshoptimizer cannot recover instancing after that
bake; preserving node/mesh sharing is a separate importer and scene-model
change that should be evaluated before making large content-size promises.

An explicitly tagged geometric decal material also bakes its validated
world-space normal clearance during that transform step. The displacement is
therefore part of the source geometry seen by range-local bounds and version-15
quantization. Cooked decode and both GPU backends need no decal metadata,
material-name heuristic, polygon offset, or per-draw branch. The exact authoring
field and validation rules are specified in
[gltf-loader-design.md](gltf-loader-design.md#geometric-decal-clearance).
For externally distributed models, tracked `<source>.vkr.json` files carry the
same explicit material values and enter the cooked dependency hash. Mesh
regeneration is explicit: run `tools/cook_vkr_meshes.sh` or
`tools/cook_vkr_meshes.bat` after changing a source model or sidecar.
Application build wrappers never recook `.vkb` artifacts; they run only the
texture packer after compilation. Standalone cooks skip absent local model
sources. With `VKR_MESH_COOK_STRICT_INPUTS=1`, every present source must have
its tracked import sidecar.

### GPU representation

`VkrVertex3d` remains a 64-byte import/procedural representation. Every static
publication is normalized to `VkrPackedStaticVertex`, a reflected 32-byte ABI:
position UNORM16, octahedral normal/tangent, float32 UV, RGBA8 color, and
tangent sign. Vulkan and Metal allocate and upload that layout plus one 32-byte
position decode record per renderable range and 32-bit indices.

The resident raw geometry contract is:

```text
static GPU payload = 32 * vertex_count + 4 * index_count
                   + 32 * range_count bytes
```

The loader may pass a 16-bit index buffer, but Vulkan expands it to 32-bit for
the megabuffer. Any claim that a 16-bit cooked index saves Vulkan VRAM is false
until the publisher and draw ABI support it.

The existing address-based vertex-pulling path is the right place to change
this. A `VkrGpuGeometryRow` supplies vertex and index addresses and the shader
uses `first_vertex` to pull records from the megabuffer. In the Vulkan deferred
visibility resolve and Metal G-buffer resolve, the shader reconstructs a
visible triangle by loading three full vertex records. Thus a tighter static
record can reduce megabuffer residency, upload traffic, and geometry reads in
the passes that pull those records. Cache-line behaviour, shader-generated
loads, and decode arithmetic decide the frame-time result, so byte savings do
not prove a large frame-time gain.

## Asset pipeline

### Offline artifact boundary, implemented

The existing `.vkb` extension is the deterministic cooked artifact.
`vkr_mesh_cooker` consumes source OBJ/glTF/GLB and atomically writes immutable
version-15 `.vkb` files. Source formats remain authoring inputs and runtime
source loads do not write beside them. Production scenes reference artifacts
generated by the platform cook scripts. Those wrappers run the shared texture
packer after mesh cooking because glTF import can create material derivatives;
success therefore includes their required `.vkt` siblings. Generated material
files referenced by cooked ranges remain in the dependency manifest.

The cooker keeps persistent importer state in a source arena and parser/codec
temporaries in an independent scratch arena. Parser scope rollback therefore
cannot invalidate accumulated vertices, ranges, or dependency paths.

The version-15 `.vkb` header contains:

- magic, format version, endianness, and explicit meshoptimizer codec version;
- a content hash of all source/dependency bytes and a cooker-settings hash;
- layout identifier, a first-range header summary, and authoritative per-range
  decode parameters in each range directory entry;
- exact byte ranges, encoded/decoded sizes, alignment, and checksum for every
  vertex and index stream;
- range/submesh metadata, material identifiers, bounds, and dependency data,
  covered by a separate metadata checksum.

All untrusted lengths and offsets are validated once at the file boundary
before dependency I/O or result-buffer allocation. Invalid artifacts fail the
request; they never reach a publisher with partly decoded data.

### Cook order per independent renderable range

A range maps to the current material/submesh boundary. The cooker must preserve
triangle ownership, material selection, bounds, and visible appearance. It
processes each range in this order:

1. establish the exact deduplication policy and generate an index buffer;
2. remove degenerate/duplicate triangles only when the chosen renderer
   semantics permit it;
3. optimize index order for vertex reuse;
4. optionally optimize overdraw, behind target-specific evidence because tiled
   GPUs need not benefit;
5. reorder vertices for fetch locality;
6. quantize into the selected packed runtime vertex representation;
7. encode optimized vertex and triangle-index streams with meshoptimizer.

This follows meshoptimizer's required locality-before-codec order. Its codec is
lossless over the bytes supplied to it; quantization is the separately specified
lossy operation. The cooker records quantization error and rejects input that
exceeds the range's configured position, normal/tangent, UV, or color error
budget.

Version 15 encodes the 32-byte packed static layout and 32-bit indices.
Deduplication and tangent generation remain in the source importer; the cooker
then applies vertex-cache and vertex-fetch optimization per range, packs with
explicit error budgets, and codec-encodes the final bytes. It does not remove
triangles or run overdraw optimization.

The packed-geometry cold boundary repairs a finite zero or normal-parallel
tangent with a deterministic orthogonal basis before octahedral encoding. It
still rejects a non-finite tangent, an invalid handedness sign, or a degenerate
normal. This makes degenerate-UV source triangles cookable without admitting an
undefined shader tangent frame.

Pull meshoptimizer through a pinned `vendor/meshoptimizer` git submodule. This
matches the existing `vendor/ktx-software` pattern: the checkout is part of the
source tree, CMake builds it as a static child target, and configure fails with
a direct `git submodule update --init --recursive` instruction when it is
missing. Do not use `FetchContent` or any configure-time network download.

The reviewed dependency is meshoptimizer v1.2 at commit
`9d9890c73011d75920af614485296d1e03e95448`. Its MIT license remains in the
pinned submodule. Updates require an explicit dependency review; do not copy
files into VKR. That would create a snapshot with less upgrade provenance than
the submodule.

meshoptimizer source is C++. The internal `vkr_meshoptimizer_bridge` target
links the static upstream target and exports only VKR-owned `extern "C"`
functions to the C11 loader and cooker. Its header stays private to the mesh
pipeline, and final targets acquire the C++ runtime through target
dependencies. Public VKR headers and per-draw code expose neither C++ nor
meshoptimizer types.

### Runtime `.vkb` load, implemented

`vkr_mesh_loader_create()` remains the sole mesh loader. Its `can_load` and
source dispatch retain `.vkb`; no new resource type, extension, or scene API is
needed.

1. Worker `prepare_async` validates the complete `.vkb` structure, metadata and
   stream checksums, codec headers, and dependency hash.
2. It decodes streams into the result arena in their already packed runtime
   representation, creates the existing submesh ranges, and records material
   dependency requests.
3. `finalize_async` retains its render-thread material resolution and
   publication contract. Load metrics flow into frame metrics, and both
   publishers account vertex, index, and decode-metadata upload/residency.
4. Unload continues to release the loader result, material request references,
   and finally GPU resources through their existing proven-submit retirement
   path.

The decoder is CPU work and belongs to the worker stage. There is no per-draw
decode, allocation, lookup, or fallback branch.

Dependency paths, sizes, and hashes remain in metadata covered by the artifact
checksum, but runtime decode performs no dependency filesystem I/O. The cook
step owns freshness; deployment may omit authoring sources. Remote or untrusted
distribution still requires a signed publication manifest because CRC32 and
source provenance are not an authenticity boundary.

The source-free contract is the geometry boundary, not a ban on separate
scene metadata. A scene mesh may explicitly name `mesh.gltf_light_source`;
the scene loader reads that glTF only for transformed `KHR_lights_punctual`
nodes. An unreadable or malformed explicit light source fails the scene load
instead of activating the cooked geometry without its authored lights. Bistro
uses this split: `bistro-lights.vkb` supplies geometry and
`bistro-lights.gltf` supplies 72 point lights plus one directional-light node.

Cache terminology is explicit: `.vkb` and `.vkt` are persistent cooked asset
artifacts, while the resource system deduplicates live requests only within one
process. Harness `cache: isolated_cold|isolated_warm|shared` controls the GPU
pipeline cache, not mesh decode, texture transcode, or cross-process asset
residency; every harness repetition starts a new renderer process.

Focused tests cover deterministic encoding, quantization-budget rejection,
SHA-256 provenance metadata, source-free direct loader dispatch, valid packed
range reconstruction, malformed offsets/checksums/codecs, repeated sync
load/unload, async cancellation, and malformed async failure with pool capacity
returning to baseline.

### Runtime source optimization, second implementation

The runtime path is a separate implementation, not a fallback hidden inside
the cooker and not a way to create a `.vkb` during gameplay. It applies to
every source OBJ/glTF/GLB request. Cooked `.vkb` decodes its stored optimized
representation and never passes through the runtime optimizer.

The optimizer runs inside mesh `prepare_async` after source parsing and before
the result is retained for finalization. Scoped worker scratch owns remaps and
transient buffers; only final packed buffers enter the mesh-result arena. The
mesh result retains no optimizer scratch state.

Cache and vertex-fetch ordering operate on the imported `VkrVertex3d` data,
then the source result packs into the static GPU ABI. Overdraw optimization
remains excluded because its value depends on target GPU and pass topology.

The source request identity remains `<type>|<path>`. Every request produces the
same optimized result, so deduplicated consumers need no policy dimension in
the resource key and there is no configuration or environment-variable bypass.

Keep the two paths distinct in code and test them independently:

```text
offline: source -> vkr_mesh_cooker -> .vkb -> loader decode
runtime: source -> loader parse -> runtime optimize -> result arena -> publish
```

They may share a small, pure range-optimization helper and common test vectors.
They must not share mutable cache state, source rewriting, or any policy branch
in the per-draw path.

### Packed GPU ABI, third implementation

ADR-031 is implemented as one 32-byte static GPU record:

| field | storage | decode authority |
| --- | --- | --- |
| words 0–1 | position UNORM16×3; tangent sign, remaining bits zero | range-local scale and bias |
| word 2 | octahedral normal SNORM16×2 | vertex/resolve shader |
| word 3 | octahedral tangent SNORM16×2 | vertex/resolve shader |
| words 4–5 | UV float32×2 | direct |
| word 6 | color RGBA8 UNORM | vertex/resolve shader |
| word 7 | reserved zero | ABI validation |

Cooked artifacts store this representation directly. Source meshes pack after
mandatory cache/fetch optimization, and procedural legacy configs pack at the
geometry-system publication boundary. A persistent contiguous decode array
stores one 32-byte scale, bias, and format record per renderable range;
`VkrGpuGeometryRow.decode_address` references its base. Candidate and visible
rows carry the range's validated `decode_index`, so raster, shadow,
transmission, picking, and deferred reconstruction select the same record. C,
Slang, native MSL, Metal reflection, and Vulkan reflection validate the same
record sizes and field offsets.

The first 24-byte candidate used float16 UVs. New Sponza range 26 exceeded the
absolute UV budget by orders of magnitude because production tiled UVs exceed
float16's useful precision. Retaining float32 UVs expands the record to 32 bytes
but removes the content-dependent failure and restores natural record
alignment.

Vertex and visibility-resolve pull loops decode only the packed layout; there
is no hot-loop layout test. `VkrVertex3d` remains the source/procedural
compatibility representation before cold-boundary packing. Position/attribute
stream splitting remains deferred because current resolve paths consume every
attribute for each reconstructed triangle.

The layout continues to use 32-bit indices. A 16-bit path needs explicit
index-type partitioning in draw encoding and visibility resolve; loader input
size alone cannot safely select it.

The exact storage reduction is 64 to 32 bytes per vertex, or 50%. With three
32-bit indices per vertex, total raw geometry falls from 76 to 44 bytes per
vertex-equivalent, or 42.1%, before alignment and fragmentation. This is
storage arithmetic, not a frame-time claim.

### glTF compression support

`mesh_loader_gltf.c` decodes `EXT_meshopt_compression` buffer views after
`cgltf_load_buffers()` and before accessor reads. The loader validates source
offsets and sizes, decoded `count × stride`, mode, and filter; decoded buffers
remain request-owned until cgltf teardown completes.

Supported modes are `ATTRIBUTES`, `TRIANGLES`, and `INDICES`. Supported filters
are `NONE`, `OCTAHEDRAL`, `QUATERNION`, `EXPONENTIAL`, and `COLOR`.
`KHR_meshopt_compression` is rejected when required. This interoperability
feature is independent of the version-15 `.vkb` runtime artifact contract.

Meshlets, LOD simplification, GPU-side decode, skinning, and animation
compression remain out of scope. Meshlets need a mesh-shader/cluster draw
contract; adding their codec to indexed draws would add storage without a
consumer.

## Rollout and evidence

1. **Baseline — implemented.** Metrics cover source, cooked, decoded, uploaded,
   and resident bytes; vertex/index/decode occupancy and high-water values;
   counts; and meshoptimizer cache/fetch analyzers.
2. **Cooker — implemented.** The pinned static dependency, private bridge,
   version-15 writer, deterministic byte comparison, quantization budgets,
   malformed-artifact coverage, and packed round trip ship.
3. **Cooked runtime load — implemented.** Worker decode validates bounded
   metadata, checksums, codecs, bounds, quantization, and the integrity of
   embedded dependency provenance without authoring-source I/O. Repeated sync
   load/unload, async cancellation, and malformed async failure return pool
   capacity to baseline.
4. **Runtime optimizer — implemented.** Every source OBJ/glTF/GLB request
   applies cache/fetch optimization; cooked loads bypass it. Tests cover
   deterministic output, source topology, range/material identity, and scratch
   lifetime.
5. **Tight packed GPU ABI — implemented.** Both selected backends publish the
   32-byte static record plus decode metadata and use branchless packed pulls.
   The 24-byte candidate failed the UV budget on representative production
   content.
6. **16-bit index ABI — deferred.** It requires explicit draw/resolve
   partitioning; no hot-loop index-type branch or implicit widening is accepted.
   Revisit with matched backend evidence that the extra path improves the
   measured workload.
7. **Interop — implemented.** glTF `EXT_meshopt_compression` decoding has
   encoded-stream importer coverage. Error-bounded LOD remains a separate
   feature.

## Acceptance criteria

- Every cooked range decodes to valid indices, valid bounds, and the declared
  material/range order; malformed offsets, sizes, hashes, and codec failures
  are rejected before publication.
- Repeated scene load/unload returns loader-arena/pool capacity and material
  references to their baseline; GPU geometry slot reuse remains gated by proven
  completion.
- Visual/capture comparison stays within the approved per-attribute error
  budgets on both selected implementations.
- Runtime optimization preserves the source mesh's material/range order and
  renderable output, has no allocations after `prepare_async` returns, and
  cannot cause two callers with different policies to share a request.
- The after report contains the same Release configuration, scene/camera,
  warm-up policy, artifact hashes, source/cooked/decoded/upload/GPU byte counts,
  and frame-time percentiles as the baseline. A size reduction without a
  measured runtime result is reported as storage-only.
- The packed-ABI report separately records vertex/resolve GPU times, packed
  decode metadata bytes, vertex/index live and high-water bytes, and the
  quantization error maxima. It may call the result a frame-time improvement
  only when the same Release profile shows it.
